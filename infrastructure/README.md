# JobForge — Local Infrastructure (Phase 0)

Owner: **Dev 3 (infra lane)**. Spec: `docs/ARCHITECTURE.md` §14, §15, §21, §27 and `docs/DATABASE_SCHEMA.md` §2.
Everything is free/open-source. **No paid service or API key is needed.** `AI_PROVIDER` defaults to `local`.

## What Phase 0 provides

| Service | Image (default tag) | Host port (127.0.0.1) | Health check | Purpose |
|---|---|---|---|---|
| `postgres` | `postgres:16` | 5432 | `pg_isready` over TCP | One DB `jobforge`, schemas `core`, `community`, `platform`, `ai` |
| `redis` | `redis:7-alpine` | 6379 | `redis-cli ping` | Cache, rate limits, quota counters, pub/sub (TTL-only eviction) |
| `kafka` | `apache/kafka:3.8.0` (KRaft) | 9092 | `kafka-topics.sh --list` | Events (single broker, auto-create OFF) |
| `kafka-init` | same | — | exits 0 when done | Creates the 16 contract topics |
| `mailpit` | `axllent/mailpit:latest` | SMTP 1025, UI 8025 | `/mailpit readyz` | Local SMTP sink + web UI |

Not in Phase 0 (added later by their owners/phases): backend/ai-service/frontend containers, MinIO, Kafka UI, monitoring, Ollama, ClamAV. No Dockerfiles are needed yet because every service uses an official image.

Ports bind to `127.0.0.1` only (not your LAN). Approx. memory: ~1.5 GB (limits: Postgres 512 MB, Redis 320 MB, Kafka 1 GB, Mailpit 128 MB).

## Prerequisites

Docker Engine or Docker Desktop with Compose v2 (`docker compose version`), Bash (Git Bash/WSL on Windows). Free.

## Quick start

```bash
bash infrastructure/scripts/gen-secrets.sh     # creates .env (random local secrets, git-ignored)
docker compose up -d                            # or: bash infrastructure/scripts/dev-up.sh (up + verify)
bash infrastructure/scripts/verify.sh           # health + functional checks
```

Stop: `docker compose down`. Wipe all data (re-runs init scripts): `bash infrastructure/scripts/dev-reset.sh`.

## Connecting your apps (apps run natively on your host in the daily loop)

| Need | Value |
|---|---|
| PostgreSQL (backend) | `jdbc:postgresql://localhost:5432/jobforge`, user `jobforge_backend`, password `DB_PASSWORD` |
| Flyway (backend, all schemas) | user `jobforge_owner`, password `DB_MIGRATION_PASSWORD` |
| PostgreSQL (ai-service) | user `jobforge_ai`, password `AI_DB_PASSWORD` (schema `ai` only) |
| Redis | `localhost:6379` (+ `REDIS_PASSWORD` if set) |
| Kafka from host | `localhost:9092` |
| Kafka from a container on `jobforge-net` | `kafka:19092` |
| SMTP | `localhost:1025` (no auth required), inbox UI `http://localhost:8025` |

The Postgres superuser (`POSTGRES_USER`/`POSTGRES_PASSWORD`) is for infrastructure only; applications never use it.

## Database bootstrap (`infrastructure/postgres/init/`)

Runs **once**, on first start of an empty volume, in this order:

1. `01-extensions.sql` — `citext`, `pg_trgm`, `unaccent`.
2. `02-roles.sql` — `jobforge_owner` (migrations, owns objects), `jobforge_backend` (DML on core/community/platform), `jobforge_ai` (DML on `ai`). Passwords come from env via psql `\getenv` (PG ≥ 15).
3. `03-schemas.sql` — creates the four schemas owned by `jobforge_owner`, grants `USAGE`, and sets default privileges so tables created by Flyway automatically give DML to the right runtime role.

Flyway guidance (details in `docs/requests/REQ-20261001-db-bootstrap-and-kafka-listeners.md`): connect as `jobforge_owner`, one Flyway run per schema (`defaultSchema` + history table inside that schema), `createSchemas=false`. `core.audit_logs` must have `UPDATE/DELETE` revoked from `jobforge_backend` by Dev 1's core migration.

## Kafka topics

`jobforge.{users,jobs,applications,interviews,community,moderation,ai,audit}.v1` and the same with `.dlq` suffix (3 partitions, RF 1; 7-day retention, DLQ 14 days). Created by `infrastructure/kafka/create-topics.sh` (idempotent; re-run with `docker compose run --rm kafka-init`). Adding a topic = contract change (ARCHITECTURE §14) + edit that script.

## Environment configuration

- `.env.example` (committed) is the index of every variable (ARCHITECTURE §27) with **placeholders only**. `.env` (git-ignored) is generated by `gen-secrets.sh`; Compose reads it automatically.
- Required Compose variables fail fast with a helpful message if missing. Image tags and host ports are overridable.
- `ANTHROPIC_API_KEY` is **not** required and is commented out; it is only ever read by `ai-service` in a future phase with `AI_PROVIDER=claude`.
- Only `NEXT_PUBLIC_*` variables may reach the browser, and they must never contain secrets.

## Scripts (`infrastructure/scripts/`)

| Script | Purpose |
|---|---|
| `gen-secrets.sh [--force]` | Create `.env` from `.env.example` with random secrets (mode 600) |
| `dev-up.sh` | Generate `.env` if needed, `docker compose up -d`, run verify |
| `dev-reset.sh [--yes]` | `docker compose down -v` (destroys local data) |
| `verify.sh` | Waits for health checks; checks schemas, extensions, roles, privilege isolation, role logins, Redis TTL round trip, 16 Kafka topics, Mailpit readiness |

## Validating the configuration (also what `infra-ci.yml` should run)

```bash
docker compose --env-file .env.example config --quiet   # syntax + variable interpolation, placeholders are enough
docker compose config --quiet                           # with your real .env
```

## Troubleshooting

- **Port already in use:** set `POSTGRES_HOST_PORT`, `REDIS_HOST_PORT`, `MAILPIT_*_HOST_PORT` in `.env` (Kafka's 9092 is fixed because it is the advertised listener).
- **Role/schema errors after changing passwords or init scripts:** init only runs on an empty volume → `dev-reset.sh`.
- **Kafka unhealthy on first start:** it needs up to ~60 s; check `docker compose logs kafka`. After an unclean shutdown, `dev-reset.sh`.
- **Windows:** keep LF line endings (`.gitattributes` enforces it); run scripts from Git Bash or WSL.
- **Mailpit not receiving mail:** backend must use `MAIL_HOST=localhost`, `MAIL_PORT=1025`.
- **Pinning images:** `MAILPIT_IMAGE_TAG` defaults to `latest`; pin it to a specific release once chosen.

## Security notes

Local-only secrets generated per developer; nothing secret is committed; ports are loopback-bound; runtime DB roles have no DDL rights and cannot see each other's schemas; Kafka/Redis/Mailpit have no auth in dev (not for production use — production hardening is Phase 6/7).
