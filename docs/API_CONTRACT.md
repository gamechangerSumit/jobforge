# JobForge — API Contract

> **Version:** v1 (`/api/v1`). Source of truth for all HTTP behavior between frontend, backend, and ai-service.
> Machine-readable snapshot (generated by backend CI, never hand-edited): `docs/openapi/openapi.v1.json`.
> Enums referenced here are defined in `DATABASE_SCHEMA.md` §3.

Legend — **Auth:** `P` public, `A` any authenticated, `S` JOB_SEEKER, `R` RECRUITER, `AD` ADMIN. **Owner:** `D1`/`D3` implementing developer. Dev 2 consumes everything.

---

## 1. Conventions

- Base path: `/api/v1`. JSON only (`application/json; charset=utf-8`), except multipart uploads.
- Field names: `camelCase`. Enum values: `UPPER_SNAKE_CASE`. Paths: lowercase kebab-case, plural nouns.
- IDs: UUID strings. Timestamps: ISO-8601 UTC with `Z` (`2026-01-31T10:15:30Z`). Dates: `YYYY-MM-DD`.
- Money: `{ "min": 1200000, "max": 1800000, "currency": "INR", "period": "YEAR" }` (`period`: `YEAR|MONTH|HOUR`; integers, currency ISO-4217).
- Location: `{ "city": "Nagpur", "state": "Maharashtra", "country": "IN" }` (country ISO-3166 alpha-2).
- `PATCH` = partial update (JSON Merge Patch semantics; absent = unchanged, `null` = clear where nullable). `PUT` = replace or idempotent set.
- Unknown request fields are **rejected** (400 `VALIDATION_FAILED`). Unknown response fields must be **ignored** by clients.
- Server never returns `passwordHash`, token hashes, internal IDs of other schemas, or other users' emails (except to authorized recruiters/admins where stated).

## 2. Versioning and Deprecation

- Version in the URL: `/api/v1`. Additive changes (new optional fields, endpoints, enum values documented as extensible) are allowed within v1. **Clients must tolerate new enum values** in responses.
- Breaking changes (removal/rename/semantic change) require `/api/v2` for the affected resources or an expand/contract rollout documented in `CHANGELOG_CONTRACTS.md`.
- Deprecation: response header `Deprecation: true` and `Sunset: <date>`; minimum 60 days notice.
- OpenAPI snapshot drift fails CI (backend regenerates and diffs).

## 3. Authentication

- `POST /auth/login` returns `accessToken` (JWT, 15 min) in the body and sets cookie `jf_refresh` (`HttpOnly; Secure; SameSite=Strict; Path=/api/v1/auth; Max-Age=14d`).
- Clients send `Authorization: Bearer <accessToken>`. Access token lives **in memory only** (never localStorage).
- `POST /auth/refresh` (cookie + header `X-Requested-With: JobForge`) rotates the refresh token and returns a new access token. Reusing a rotated refresh token revokes the whole token family (401 `AUTH_REFRESH_REUSED`).
- JWT claims: `sub` (userId), `role`, `ver` (token version), `iat`, `exp`, `jti`. Authorization is always re-checked server-side; claims are not trusted for ownership.
- Frontend dev uses Next.js rewrites so browser calls are same-origin `/api/v1/**`.
- Internal (backend → ai-service) auth is separate: §15.

## 4. Standard Response Format

**Single resource / action result** — `200/201`:
```json
{ "data": { "id": "..." }, "meta": { "requestId": "b7f1...", "timestamp": "2026-01-31T10:15:30Z" } }
```
**Offset-paginated list** — `200`:
```json
{
  "data": [ { } ],
  "meta": {
    "requestId": "...", "timestamp": "...",
    "page": { "number": 0, "size": 20, "totalElements": 135, "totalPages": 7, "hasNext": true }
  }
}
```
**Cursor-paginated list** — `200`:
```json
{ "data": [ { } ], "meta": { "requestId": "...", "timestamp": "...", "cursor": { "next": "opaque-or-null", "hasNext": true, "limit": 20 } } }
```
- `201 Created` returns the created resource and a `Location` header.
- `204 No Content` for deletes and idempotent set/unset (`PUT/DELETE .../like`), no body.
- Empty list = `200` with `"data": []`, never `404`.
- Response header `X-Request-Id` always present (echoes client value if valid UUID, else generated).

## 5. Error Format

All non-2xx responses:
```json
{
  "error": {
    "code": "VALIDATION_FAILED",
    "message": "One or more fields are invalid.",
    "status": 400,
    "requestId": "b7f1...",
    "timestamp": "2026-01-31T10:15:30Z",
    "path": "/api/v1/jobs",
    "details": [ { "field": "title", "code": "SIZE", "message": "must be between 3 and 120 characters" } ]
  }
}
```
`message` is safe for display. `details` is optional (validation only). Stack traces, SQL, class names, and provider raw errors are **never** exposed.

### 5.1 Error code catalog (extend only via contract change)

| HTTP | Code | Meaning |
|---|---|---|
| 400 | `VALIDATION_FAILED` | Bean/field validation failure; `details[]` present |
| 400 | `MALFORMED_REQUEST` | Unparseable JSON, bad parameter type, unknown field |
| 401 | `AUTH_UNAUTHENTICATED` | Missing/invalid token |
| 401 | `AUTH_TOKEN_EXPIRED` | Access token expired → call refresh |
| 401 | `AUTH_INVALID_CREDENTIALS` | Wrong email/password (never reveals which) |
| 401 | `AUTH_REFRESH_INVALID` / `AUTH_REFRESH_REUSED` | Refresh token bad / reuse detected |
| 403 | `ACCESS_DENIED` | Role or ownership check failed |
| 403 | `EMAIL_NOT_VERIFIED` | Action needs verified email |
| 403 | `ACCOUNT_SUSPENDED` | User suspended |
| 403 | `RECRUITER_NOT_APPROVED` / `COMPANY_NOT_VERIFIED` | Publish preconditions (D-16) |
| 404 | `RESOURCE_NOT_FOUND` | Missing **or** not visible to caller (prevents ID probing) |
| 409 | `CONFLICT` | Generic uniqueness/conflict |
| 409 | `EMAIL_ALREADY_REGISTERED`, `HANDLE_TAKEN`, `DUPLICATE_APPLICATION` | Specific conflicts |
| 409 | `INVALID_STATE_TRANSITION` | Status machine violation |
| 409 | `STALE_VERSION` | Optimistic lock (`If-Match`/`version` mismatch) |
| 413 | `PAYLOAD_TOO_LARGE` | Body/upload too big |
| 415 | `UNSUPPORTED_MEDIA_TYPE` | Wrong content type / file type |
| 422 | `BUSINESS_RULE_VIOLATED` | Valid syntax, violates domain rule (message explains) |
| 429 | `RATE_LIMITED` | Has `Retry-After` |
| 429 | `AI_QUOTA_EXCEEDED` | Has `Retry-After` and `details` with reset time |
| 500 | `INTERNAL_ERROR` | Unexpected; `requestId` for support |
| 502 | `AI_OUTPUT_INVALID` | Provider output failed schema/validation after retries |
| 503 | `AI_PROVIDER_UNAVAILABLE` | ai-service/provider down or circuit open |
| 504 | `AI_TIMEOUT` | ai-service timeout |

Validation `details[].code` uses Bean Validation names (`NOT_BLANK`, `SIZE`, `EMAIL`, `PATTERN`, `MIN`, `MAX`, `INVALID_ENUM`, `UNKNOWN_FIELD`).

## 6. Pagination

- **Offset** (admin tables, job search, application lists): `page` (0-based, default 0), `size` (default 20, max 100). Response `meta.page`.
- **Cursor** (community feed, comments, notifications, AI request history): `cursor` (opaque), `limit` (default 20, max 50). Response `meta.cursor`. Cursors are opaque, signed, expire in 24 h; do not parse.
- Ordering is always deterministic (tie-breaker `id`).

## 7. Filtering

Flat query params, per-endpoint whitelist (unknown filter → 400). Conventions:
- Equality: `status=PUBLISHED`. Multi-value: repeated or comma-separated (`skills=java,spring` or `skills=java&skills=spring`), OR within one field, AND across fields (except `skills`, see §12.4).
- Ranges: `salaryMin`, `salaryMax`, `postedAfter`, `postedBefore`, `from`, `to`.
- Text: `q` (full-text).
- Booleans: `true|false`.

## 8. Sorting

`sort=<field>,<asc|desc>`; repeatable (max 2). Whitelisted per endpoint; default documented per endpoint. Invalid field → 400. Example: `sort=postedAt,desc`.

## 9. Headers, Idempotency, Rate Limits

| Header | Direction | Purpose |
|---|---|---|
| `Authorization` | req | Bearer access token |
| `X-Request-Id` | both | Correlation |
| `Idempotency-Key` | req | **Required** on `POST /jobs/{id}/applications` and `POST /ai/*` generation endpoints; UUID; 24 h window; same key + same body → replay original response (`Idempotency-Replayed: true`); same key + different body → 409 `CONFLICT` |
| `If-Match` | req | Optional `"<version>"` on `PATCH` of jobs, profiles, companies, applications; mismatch → 409 `STALE_VERSION` |
| `X-RateLimit-Limit/Remaining/Reset` | resp | Current bucket |
| `Retry-After` | resp | Seconds (429/503) |

Rate-limit classes (per authenticated user; per IP when anonymous): `AUTH` 10/min (login: 5/min per IP+email), `DEFAULT` 120/min, `SEARCH` 60/min, `WRITE_COMMUNITY` 30/min, `AI` 10/min, `UPLOAD` 10/min.

## 10. Validation Limits (shared by backend Bean Validation, frontend Zod, ai-service schema)

| Field | Rule |
|---|---|
| `email` | valid, ≤254, case-insensitive unique |
| `password` | 10–64 chars, ≥1 letter and ≥1 digit, not equal to email |
| `firstName`, `lastName` | 1–60 |
| `handle` | 3–30, `^[a-z0-9_]+$`, unique |
| `headline` | ≤120 · `summary` ≤2000 · `phone` E.164 |
| `skill` (name) | 1–50 · max 50 skills per seeker |
| Job `title` | 3–120 · `description` 50–10000 (Markdown) · `requirements`/`benefits` ≤5000 |
| Job `skills` | 1–20 |
| `coverLetter` | ≤5000 |
| Post `title` ≤150 · `body` 1–10000 · tags ≤5, each 2–30 `[a-z0-9-]` |
| Comment `body` | 1–2000 |
| Resume upload | PDF/DOCX, ≤5 MB, magic-byte verified |
| Logo/avatar | PNG/JPEG/WebP, ≤2 MB |
| Markdown fields | stored as text; HTML tags stripped server-side; clients render without raw HTML |

### 12.7 Interviews (D1)

| Method | Path | Auth | Purpose |
|---|---|---|---|
| POST | `/applications/{id}/interviews` | R (company) | `{ type, scheduledAt, durationMinutes, timezone, locationOrLink, notes? }` → also moves application to `INTERVIEW` if allowed |
| GET | `/interviews` | S (own), R (company) | `from`, `to`, `status`, pages |
| GET | `/interviews/{id}` | S (own), R | Detail |
| PATCH | `/interviews/{id}` | R | Reschedule/edit (status → `SCHEDULED`, notifies seeker) |
| POST | `/interviews/{id}/cancel` | R | `{ reason }` |
| POST | `/interviews/{id}/respond` | S | `{ "response": "CONFIRM|DECLINE", "note"? }` |
| POST | `/interviews/{id}/complete` | R | Mark completed / `NO_SHOW` via `{ "outcome": "COMPLETED|NO_SHOW" }` |

**Interview object** (all endpoints; null fields omitted). The request bodies above are unchanged; this documents the response and the rules the implementation enforces.

```json
{ "id": "uuid", "applicationId": "uuid", "applicationStatus": "INTERVIEW",
  "job": { "id": "uuid", "title": "…", "company": { "id": "uuid", "name": "…", "slug": "…", "logoUrl": "…", "verified": true }, "location": { } },
  "seeker": { "id": "uuid", "handle": "…", "firstName": "…", "lastName": "…" },
  "scheduledBy": { "id": "uuid", "handle": "…", "firstName": "…", "lastName": "…" },
  "type": "PHONE|VIDEO|ONSITE", "scheduledAt": "2026-10-12T10:00:00Z", "durationMinutes": 45, "timezone": "Asia/Kolkata",
  "locationOrLink": "…", "status": "SCHEDULED|CONFIRMED|DECLINED|COMPLETED|CANCELLED|NO_SHOW",
  "seekerResponse": "PENDING|CONFIRMED|DECLINED", "seekerResponseNote": "…", "cancelledReason": "…",
  "notes": "…", "createdAt": "…", "updatedAt": "…" }
```
- `seeker` and `notes` (internal notes) are returned to recruiters only. `POST` returns 201 + `Location`; the others 200.
- Roles: seekers and recruiters only. `ADMIN` is not listed for any interview endpoint and receives 403 (ARCHITECTURE §5 shows admin "read" for interviews; this contract takes precedence). Out-of-scope interviews/applications (another company, another seeker) answer 404; an unapproved recruiter gets 403 `RECRUITER_NOT_APPROVED`.
- Scheduling: application must be `SHORTLISTED` (moved to `INTERVIEW` through the application state machine, with history, audit and `ApplicationStatusChanged`) or already `INTERVIEW` (stays); any other status → 409 `INVALID_STATE_TRANSITION`. `scheduledAt` must be in the future and at most 365 days ahead (422 `BUSINESS_RULE_VIOLATED`); `timezone` must be an IANA id and `durationMinutes` 15–480, `locationOrLink` ≤ 500 (scripting URL schemes rejected), `notes` ≤ 2000 (400). An active interview of the same application may not overlap another one (409 `CONFLICT`).
- `PATCH` is a merge patch (absent = unchanged; blank `notes` clear them) allowed in `SCHEDULED|CONFIRMED|DECLINED`. A change to type, time, duration, timezone or place sets `status` `SCHEDULED`, `seekerResponse` `PENDING`, clears the response note and notifies the seeker; an internal-notes-only change does none of that. Closed applications (`HIRED|REJECTED|WITHDRAWN`) block such changes (422).
- `cancel` (reason required) is allowed in `SCHEDULED|CONFIRMED|DECLINED`; the reason is visible to the seeker. `respond` is allowed in `SCHEDULED|CONFIRMED` before the start (repeating the stored answer is an idempotent no-op; changing CONFIRMED→DECLINED is allowed; answering a DECLINED interview needs a reschedule). `complete` is allowed in `SCHEDULED|CONFIRMED` once the start has passed (422 before). `COMPLETED`, `CANCELLED`, `NO_SHOW` are final. Any other transition → 409 `INVALID_STATE_TRANSITION`; concurrent change → 409 `STALE_VERSION`.
- `GET /interviews`: `applicationId` (narrows to one application; an application outside the caller's scope yields an empty page, not 404), `from`/`to` accept ISO instants or `YYYY-MM-DD` (UTC, inclusive), `status`, `page`, `size`; sorted by `scheduledAt` ascending; unknown parameters → 400.
- When an application becomes `WITHDRAWN` or `REJECTED`, the system cancels its open interviews (`SCHEDULED|CONFIRMED|DECLINED`) from the application events: fixed reason text, `InterviewCancelled` with `cause` `APPLICATION_WITHDRAWN|APPLICATION_REJECTED` (manual cancels carry `cause` `RECRUITER`), audit `INTERVIEW_CANCELLED` without an actor. A withdrawal notifies the recruiter who scheduled the interview; a rejection notifies nobody extra (the seeker already receives the status notification).
- Events (topic `jobforge.interviews.v1`): `InterviewScheduled`, `InterviewUpdated`, `InterviewCancelled`, `InterviewResponded` (ids, job title, schedule metadata only, never notes/reasons). Notifications: `INTERVIEW_SCHEDULED|INTERVIEW_UPDATED|INTERVIEW_CANCELLED` to the seeker, `INTERVIEW_RESPONSE` to the recruiter who scheduled it.

#### 12.9.1 Report filing — `POST /reports`

Auth: any authenticated user (`JOB_SEEKER`, `RECRUITER`, `ADMIN`); unauthenticated → `401 AUTH_UNAUTHENTICATED`. Success responses use the §4 envelope; the DTOs below are the contents of `data`.

Request:
```json
{
  "targetType": "JOB|COMPANY|USER|POST|COMMENT",
  "targetId": "uuid",
  "reason": "SPAM|HARASSMENT|SCAM|INAPPROPRIATE|MISINFORMATION|DISCRIMINATION|OTHER",
  "details": "optional text, max 1000 UTF-16 code units"
}
```
- `targetType`, `targetId`, `reason` are required; a missing field, an invalid enum value or an unknown field → `400 VALIDATION_FAILED` (unknown field: `details[].code = UNKNOWN_FIELD`, §5.1). `details` is optional, at most 1000 UTF-16 code units (`String.length()` in Java, `.length` in JavaScript; measured on the submitted value before trimming, so a character outside the Basic Multilingual Plane, such as most emoji, counts as 2), then trimmed (leading/trailing ECMAScript whitespace: the same set as the `reason` trim in §12.11.1, including non-breaking space, U+FEFF and line terminators); a value that is empty after trimming is treated as omitted and stored as none. `details` is private report text.
- **Supported targets (phased):** `JOB`, `COMPANY`, `USER`. `POST` and `COMMENT` are reserved enum values: until the Community module registers their target adapters, `POST /reports` returns `422 BUSINESS_RULE_VIOLATED` for them. Community post/comment reporting and moderation are **not** implemented; they are deferred to the Community session, and until that session is implemented and approved this `422` behavior is unchanged.
- **Visibility:** `JOB` must be currently public (published, not expired, not removed/deleted); `COMPANY` must be `VERIFIED` and not soft-deleted (a soft-deleted company is treated as missing even though its verification status is retained); `USER` must be `ACTIVE`. A missing or non-visible target → `404 RESOURCE_NOT_FOUND` (no ID probing, §5.1).
- **Self-reports:** a caller cannot report their own account, a job they created, or a company they own → `422 BUSINESS_RULE_VIOLATED`.
- **Duplicates:** at most one active report per `(reporter, targetType, targetId)` while the earlier report is `OPEN` or `REVIEWING` → `409 CONFLICT`. A new report may be filed once the earlier one is `RESOLVED` or `DISMISSED`.
- **Rate limiting:** `POST /reports` currently uses rate-limit class `DEFAULT` (§9). Decision for v1: keep `DEFAULT`; `WRITE_COMMUNITY` or a dedicated report-write class is not assigned and is not part of this contract.
- Response `201 Created` (§4); `data`:
```json
{ "id": "uuid", "targetType": "JOB", "targetId": "uuid", "reason": "SPAM", "status": "OPEN", "createdAt": "2026-10-10T10:15:30Z" }
```
  The response never echoes `details`, reporter identity or moderation data. `status` is always `OPEN` on creation.
- The `Location` header (§4) is `/api/v1/admin/reports/{id}`, the report's only resource URI. It is readable by `ADMIN` only (§12.11.1): v1 has no reporter-facing read endpoint, so a reporter following it gets `403 ACCESS_DENIED`. This URI identifies an admin resource, not a reporter-facing one; a reporter read endpoint is intentionally out of v1.

#### 12.11.1 Report moderation — `/admin/reports`

All `/admin/reports/**` endpoints are `ADMIN` only; there is no `MODERATOR` role in v1. Unauthenticated → `401 AUTH_UNAUTHENTICATED`; authenticated non-admin → `403 ACCESS_DENIED`. Success responses use the §4 envelope; the DTOs below are the contents of `data`.

**`GET /admin/reports`** — offset pagination (§6, `meta.page`). Optional query parameters: `status` (`OPEN|REVIEWING|RESOLVED|DISMISSED`), `targetType` (`POST|COMMENT|USER|JOB|COMPANY`), `reason` (report reasons above), `sort` (`createdAt,asc|createdAt,desc`; default `createdAt,asc`, oldest first), `page` (default 0), `size` (default 20, max 100). An unknown query parameter, an invalid enum value or an unsupported `sort` → `400 VALIDATION_FAILED`. Each `data[]` item (no private `details`):
```json
{ "id": "uuid", "targetType": "JOB", "targetId": "uuid", "reason": "SPAM", "status": "OPEN",
  "reporterId": "uuid", "createdAt": "2026-10-10T10:15:30Z", "updatedAt": "2026-10-10T10:15:30Z" }
```

**`GET /admin/reports/{id}`** — `200`; unknown id → `404 RESOURCE_NOT_FOUND`. Only admins can read private `details` and the reporter identity. `data`:
```json
{
  "id": "uuid", "targetType": "JOB", "targetId": "uuid", "reason": "SPAM",
  "details": "private report details (omitted when none)", "status": "OPEN",
  "reporter": { "id": "uuid", "displayName": "Reporter name" },
  "target": { "type": "JOB", "id": "uuid", "label": "Job title", "status": "PUBLISHED", "available": true },
  "actions": [ { "id": "uuid", "action": "WARN_USER", "moderatorId": "uuid", "reason": "Policy explanation", "createdAt": "2026-10-10T10:15:30Z" } ],
  "createdAt": "2026-10-10T10:15:30Z", "updatedAt": "2026-10-10T10:15:30Z"
}
```
`reporter.displayName` is `"Deleted user"` when the reporter's account no longer exists. When the target is gone or no longer visible, `target` is `{ "type", "id", "status": "UNAVAILABLE", "available": false }` (`label` omitted). `actions` is the moderation history, oldest first.

**`POST /admin/reports/{id}/resolve`** — request:
```json
{ "action": "DISMISS|HIDE_CONTENT|REMOVE_CONTENT|WARN_USER|SUSPEND_USER", "reason": "10–500 characters after trimming" }
```
- `reason` is required and trimmed (leading/trailing Unicode whitespace, including non-breaking space, U+FEFF and line terminators, is removed); the trimmed value must be 10–500 characters, counted as Unicode code points (an emoji counts as 1) → otherwise `400 VALIDATION_FAILED` (`details[].code = SIZE`). Whitespace padding neither satisfies the minimum nor counts toward the maximum. The stored/audited reason is the trimmed value. The frontend applies the same rule.
- Supported action matrix (any other combination → `422 BUSINESS_RULE_VIOLATED`, no side effects):

| Action | JOB | COMPANY | USER |
|---|---|---|---|
| `DISMISS` | Supported | Supported | Supported |
| `WARN_USER` | Supported (job creator) | Supported (company owner) | Supported (reported user) |
| `REMOVE_CONTENT` | Supported (existing admin job removal) | Unsupported | Unsupported |
| `SUSPEND_USER` | Unsupported | Unsupported | Supported (existing user moderation rules; an administrator cannot be suspended) |
| `HIDE_CONTENT` | Unsupported | Unsupported | Unsupported |

  `HIDE_CONTENT` is an enum value only; no current target has a hidden state. `POST`/`COMMENT` reports cannot exist yet (§12.9.1). Both `HIDE_CONTENT` and `POST`/`COMMENT` targets are deferred to the Community session; until then the `422` behavior above is unchanged.
- If the target has disappeared (missing, soft-deleted or no longer visible), only `DISMISS` is allowed; any other action → `422 BUSINESS_RULE_VIOLATED`.
- `DISMISS` moves an active (`OPEN`/`REVIEWING`) report to `DISMISSED`; every other supported action moves it to `RESOLVED`. `RESOLVED` and `DISMISSED` are terminal: resolving a terminal report (including a concurrent resolve) → `409 INVALID_STATE_TRANSITION`.
- One transaction records the `moderation_actions` row, the status change, and the audit entries: `REPORT_RESOLVED` for every decision, plus `CONTENT_MODERATED` for non-dismiss decisions.
- Response `200`: the updated report detail (shape above).

**Report workflow limitations (v1):** reports are created `OPEN`; `REVIEWING` is a schema-supported active status but no endpoint moves a report into it; there is no reporter-facing "my reports" endpoint; resolving `REMOVE_CONTENT` against a job that was already removed by another path is rejected by the job state machine (admins should `DISMISS`).

**Events and notifications:** `ContentReported` and `ContentModerated` are published to `jobforge.moderation.v1` with no free-text report details or moderation reason in the payload. `ContentReported` carries no user-facing notification guarantee: no report-arrival notification type or recipient policy is defined, so filing a report notifies nobody (the synchronous `REPORT_FILED` audit entry is written). Notifying admins of new reports is deferred and requires a separate approved contract change; no new consumer or notification type is introduced in v1. `ContentModerated` (non-dismiss decisions) notifies the affected target owner with a `CONTENT_MODERATED` notification and never exposes the reporter or private report details.

### 14.1 `POST /ai/job-drafts`

Request:
```json
{
  "title": "Backend Engineer",
  "companyId": "uuid",
  "experienceLevel": "MID",
  "employmentType": "FULL_TIME",
  "workMode": "HYBRID",
  "location": { "city": "Nagpur", "state": "Maharashtra", "country": "IN" },

  "tone": "PROFESSIONAL",

```
Limits: `title` 3–120, `skills` 1–20, `notes` ≤1000, `tone` ∈ `PROFESSIONAL|FRIENDLY|CONCISE`, `language` ∈ `en` (v1). `notes` is treated as **data, never instructions** (prompt-injection hardening in ai-service).

Response `200`:
```json
{
  "data": {
    "requestId": "uuid",
    "operation": "JOB_GENERATION",
    "provider": "local-template",
    "model": "template-v1",
    "schemaVersion": "job-draft.v1",
    "draft": {
      "title": "Backend Engineer",
      "summary": "≤500 chars",
      "responsibilities": ["…"],
      "requirements": ["…"],
      "niceToHave": ["…"],
      "benefits": ["…"],
      "skills": [ { "name": "java", "required": true } ],
      "employmentType": "FULL_TIME", "workMode": "HYBRID", "experienceLevel": "MID",
      "descriptionMarkdown": "Assembled Markdown of the above"
    },
    "quality": { "score": 82, "issues": [ { "code": "MISSING_SALARY", "severity": "INFO", "field": "salary", "message": "…", "suggestion": "…" } ] },
    "quota": { "creditsCharged": 5, "remaining": 95, "limit": 100, "period": "DAILY", "resetsAt": "…Z" }
  },
  "meta": { }
}
```
Draft schema limits (enforced by `job-draft.v1` JSON Schema in ai-service **before persistence**): `summary` ≤500; `responsibilities` 3–12 items ≤300 chars; `requirements` 3–12 ≤300; `niceToHave` 0–8; `benefits` 0–10; `skills` 3–20, name ≤50; enums as in DATABASE_SCHEMA §3; no HTML; no URLs/emails (PII/spam guard).

### 14.2 `POST /ai/job-validations`
